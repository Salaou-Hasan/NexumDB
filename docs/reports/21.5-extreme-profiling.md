## 7. Cross-partition messaging

`messages_sent/delivered/dropped = 0` in every profile: the arena workload
is partition-local (players interact only within their partition). This is a
true horizontal-sharding result — 8–16 partitions run fully independently
with zero cross-partition traffic in the measured workload. Cross-partition
messaging cost is therefore **not** on the critical path for this workload.

## 9. Cheap-system inventory (leave alone)

- PK lookup ≈ 45 ns, single-row update ≈ 1 µs (Phase 15, unchanged).
- Native reducers 3.9–6.6 µs/call.
- Subscription engine: **per_change = 1.00** — Phase 20's interest
  management means every change is evaluated against exactly one shared
  view per world; sub_apply is 0.3–3.4% of tick CPU.
- Tick gate, frame validation, auth: negligible (inbound 0.3 ms @ 1K).
- WAL: not on the gameplay critical path.
- Deterministic delivery, event log, metrics collection: not measurable on
  the tick (≤ 0.1% each).

## 11. Latency-spike investigation (measured)

- **p99.9 ≈ p99 in every corrected run** (e.g. A@10K 11.1/11.1 ms, B@10K
  77.7/66.6 ms, C@1K 63.8/63.8 ms). There is **no pathological tail** in
  the measured workload — the p99.9 story is the fire-burst ticks, not OS
  or allocator noise.
- The **only** reproducible spike class found was an **artificial harness
  artifact**: the warmup loop never drained client event queues, so the
  first measured tick paid the 10-tick backlog (a 220–320 ms drain spike at
  tick 0, inflating p99.9 to 300–600 ms). Fixed by draining during warmup
  (measurement fix, not a perf change).
- Remaining worst ticks (E@5K: p99 1094 ms) are the **WASM fire-burst
  ticks** — 5K fire calls ≈ 340 ms aggregate CPU plus subscription deltas,
  frame fan-out, and client decode, all on the same tick.

## 12. 20K limiting factor

Connection-only is PASS at 20K (p99 25 ms). **Gameplay at 20K is NOT
claimed.** The measured limiter is the **sum of O(CCU) per-client work**
(inbound decode + world tick + fanout + SDK decode) — already ~50 ms of the
budget at 10–15K movement — **amplified by the WASM fire burst**, which
costs ~15x the native reducer and is the single most expensive component.
Order of leverage for Phase 22+:

1. **WASM call cost** (65–69 µs → target ~10 µs): biggest single lever.
2. Per-client frame counts (fanout + SDK decode): reduce messages/client.
3. Inbound per-call overhead (Phase 23 networking).

## 13. Phase 22 recommendation (measured, not assumed)

Phase 22 — **WASM execution hot-path**:

- Baseline (measured): `fire_weapon` 65–69 µs/call vs native 3.9–4.8 µs —
  a 14–17x sandbox boundary cost; 10K fires/tick ≈ 650–750 ms aggregate CPU.
- Investigate: module/instance reuse, linear-memory reuse, allocator reuse,
  ABI argument/result encoding, host-call batching, per-reducer scheduling.
- Must not remove sandboxing; native Rust remains the max-performance path.
- Success metric: per-call WASM latency toward ~10 µs (≤ 3x native) with the
  full suite green and determinism preserved.

# ADR-001: Foundation — workspace layout and core state model

**Status:** Accepted
**Phase:** 0 (foundation) + 1 (core types and state model)
**Date:** 2026-08-11

## Context

Nexum is an authoritative state engine for realtime multiplayer and simulation
backends. The full build spans 16 phases, and the spec mandates a strict
implementation order: repository foundation → core types → tables → storage →
transactions → durability → reducers → WASM → subscriptions → simulation →
runtime → networking → SDK → query → observability → benchmarks → scaling.

The first two phases must establish a clean, understandable foundation without
prematurely creating abstractions.

## Decisions

### D1. One Cargo workspace, one crate per subsystem

A workspace (`Cargo.toml` at the root) with ten member crates under `crates/`,
mirroring the subsystem boundaries from the spec:

- `nexum-core` — types and state model (the only crate with real code so far)
- `nexum-table`, `nexum-tx`, `nexum-storage`, `nexum-reducer`,
  `nexum-subscription`, `nexum-simulation`, `nexum-runtime`, `nexum-network`
- `nexum-server` — binary crate

Rationale: the dependency graph is the architecture map. Clean crate boundaries
make the dependency graph readable, prevent circular dependencies by
construction, and keep subsystems independently testable. No giant modules, no
giant manager classes.

### D2. `nexum-core` is the dependency root

`nexum-core` depends on nothing. Every other crate depends on `nexum-core`
(declared via `[workspace.dependencies]`). This guarantees there is exactly one
authoritative definition of ids, versions, timestamps, and errors shared by all
subsystems.

### D3. Ids are typed `u64` newtypes

All identifiers — `TableId`, `RowId`, `ColumnId`, `PartitionId`,
`TransactionId`, `ReducerId`, `SubscriptionId` — are `repr(transparent)`
newtypes over `u64`, generated by a private `define_id!` macro in
`nexum-core::ids`.

- The type system prevents mixing up a table id with a row id at compile time.
- Each id implements `Copy`, `Eq`, `Ord`, `Hash`, `Display`, `From<u64>`,
  `From<id> for u64`, and the `Id` trait, so they work directly as map keys and
  convert cleanly to raw values for wire formats and storage keys.

### D4. `Version` and `Timestamp` are the concurrency/time primitives

`Version` is a monotonically increasing `u64` newtype with `ZERO` and `next()`.
It is the backbone of Optimistic Concurrency Control: every read that
participates in conflict detection carries a version; a write bumps it; a
mismatch at validation time aborts the transaction. This is the exact OCC model
the spec requires for Phase 4.

`Timestamp` is milliseconds since the Unix epoch. It serves simulation time,
WAL records, and metrics. (A logical tick counter may be added for simulation
determinism in Phase 9; `Timestamp` remains the shared representation.)

### D5. One shared `Error` type

`nexum-core::errors::Error` is a single `#[non_exhaustive]` enum covering
`NotFound`, `AlreadyExists`, `InvalidArgument`, `Conflict` (OCC aborts),
`Capacity`, `Internal`, and `Unsupported`, with ergonomic constructor helpers
and a `Result<T>` alias. One error type keeps crate boundaries clean — no
error translation layers between table, transaction, storage, and reducer
code.

### D6. Foundational state interfaces live in `nexum-core::state`

- `Id` — implemented by every id type; exposes `as_u64()` / `from_u64()`.
- `Versioned` — anything carrying a `Version` for conflict detection.
- `ChangeKind` — `Insert` / `Update` / `Delete`, the vocabulary of change
  tracking and, later, subscription deltas.

These express the one-authoritative-state philosophy: tables hold the state,
and every other system (transactions, subscriptions, WAL, snapshots) is derived
infrastructure operating through these shared interfaces.

### D7. Schema primitives will live in `nexum-core::schema`

Table schema definitions are needed by `nexum-table`, `nexum-tx`, and
`nexum-storage` alike. Putting them in `nexum-core::schema` (rather than inside
`nexum-table`) prevents duplicated type definitions and circular dependencies.
The module is intentionally empty until Phase 2 defines the concrete schema
types.

### D8. No unsafe code, no external dependencies yet

`unsafe_code = "forbid"` is set at the workspace level. `nexum-core` has zero
dependencies. The networking and serialization crates will add dependencies
(QUIC, protobuf, etc.) only when their phases arrive — not before.

### D9. Empty scaffolding is documentation, not code

Scaffold crates contain only module-level documentation describing their
planned subsystem and phase. No placeholder structs, no fake abstractions, no
empty traits. The spec says: *Do not prematurely create hundreds of
abstractions.* The code will appear with its phase.

## Consequences

- The workspace builds and tests cleanly today (`cargo build --workspace`,
  `cargo test --workspace`).
- Phase 2 (tables) can start by filling in `nexum-table` and `nexum-core::schema`
  without touching the rest of the workspace.
- The dependency graph is acyclic and readable; adding a new subsystem is a
  new crate plus a workspace member entry.
- Because `Error` and the id/version types are shared, later phases (WASM host
  API, wire protocol) will not need to translate between error domains.

## Open questions

- Exact allocation scheme for ids (monotonic counters vs. partition-scoped
  ids) — deferred until the runtime phase.
- Whether `Timestamp` should also carry a logical tick — deferred to Phase 9.

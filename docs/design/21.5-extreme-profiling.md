# Phase 21.5 — Extreme Execution Profiling & Hot-Path Audit: Design

Status: complete. This is an **investigation phase**: the full authoritative
execution pipeline was instrumented and measured at phase, sub-phase,
per-reducer, and allocation granularity. No optimizations were performed —
the output is a ranked cost map plus the Phase 22+ roadmap.

## 1. Purpose

Answer with measurements, not assumptions:

- Where does execution time actually go (per phase, per tick)?
- Which systems are expensive / cheap / scaling badly?
- How much work is done per client, per change, per tick?
- Where are the allocation hotspots? The synchronization hotspots?
- What causes the p99/p99.9 tail?
- What exactly limits 20K realistic gameplay CCU?

## 2. Instrumentation added (measurement only, zero semantic impact)

### 2.1 Per-reducer execution profile

- `SimulationConfig::with_reducer_profiling(bool)` (default **false**; zero
  cost when off).
- `World` accumulates `name → (calls, cumulative wall ns)` for every reducer
  invocation in a tick: phase 0a handlers (cross-partition messages),
  phase 0b scheduled events, phase 0c client calls (native or WASM).
- `Runtime::reducer_profile()` aggregates across all worlds in deterministic
  order.
- `GameServerConfig::with_reducer_profiling(bool)` plumbed into both world
  creation and recovery paths.
- Harness flag `--reducer-profile` diffs the profile across the measured
  phase and prints calls / total ms / average µs per reducer.

### 2.2 Counting global allocator

- New tiny crate `nexum-alloc-count`: a `#[global_allocator]` that forwards
  to `System` and counts allocations / bytes / frees with relaxed atomics.
  It is the **only** crate implementing `unsafe impl GlobalAlloc` — it
  deliberately does not inherit `[workspace.lints]` so every other Nexum
  crate keeps `unsafe_code = forbid`. The `unsafe` lives inside this one
  instrumentation crate, which is the unavoidable contract of `GlobalAlloc`.
- Installed in the CCU harness only under the `ccu-alloc` feature
  (`--features ccu-alloc`); counting is disabled by default (a single
  relaxed load per allocation), so the **timing ladder is unperturbed**.
- Harness flag `--count-alloc` reports allocs/tick, bytes/tick,
  allocs/client/tick, bytes/client/tick, frees/tick.

### 2.3 Tail-latency and spike instrumentation

- Harness now reports **p99.9 and max** alongside p50/p95/p99/avg.
- `--profile-detail` records a **per-tick phase sample** (inbound, tick,
  fanout, pump, flush, clients, drain) and prints the five worst ticks with
  their phase composition — answering "what happened during the spike?"
- Warmup now drains clients (previously the accumulated warmup backlog
  surfaced as an artificial tick-0 p99.9 spike).

### 2.4 Instrumentation fixes (correctness of the measurements)

- `RuntimeMetrics.last_tick_profile` previously kept only the **last
  world's** sub-phase times, under-reporting by ~N× at N partitions. It now
  **accumulates across the step's worlds** and is reset at the start of each
  step (`step`, `step_detailed`), so world_tick / wal / sub_apply are the
  tick's true aggregate.
- `pump` (subscription pump) is now timed separately from `fanout` (it was
  folded into fanout and the `pump` accumulator was never filled).

## 3. Workload definitions (harness, real stack)

All profiles run the **real** stack: Gateway → Runtime → World → reducers
(native + WASM) → Transaction/OCC → commit → `Vec<Change>` →
SubscriptionRegistry → SDK clients over in-process transport. The socket
layer is in-process; protocol, codec, gateway, runtime, world,
subscriptions, and SDK views are real.

- `A` — connection only: 10K/20K idle TickUpdates broadcast per tick.
- `B` — light input: every client moves every 4th tick (≈5 Hz).
- `C` — realistic: movement every 3rd tick + a WASM fire burst every 100
  ticks (every 5 s).
- `D` — stress: every client moves every tick + fire burst every 4th tick.
- `E` — extreme (new): every client moves **every tick**, fires every 10
  ticks (≈2/s), reloads every 25 ticks — native move + WASM fire + native
  reload + subscriptions + decode + drain active every tick.

## 4. Measurement methodology

- Release build, LTO fat, single codegen unit (Phase 16 profile).
- 20 Hz tick budget = 50 ms. Classification: PASS p99 < 50 ms; DEGRADED
  50 ≤ p99 < 100 ms; SATURATED p99 ≥ 100 ms.
- 10-tick warmup (now with client drain) before the measured phase.
- Phase timings are cumulative `Instant` deltas averaged over the measured
  ticks; `world_tick/wal/sub_apply` are the runtime's aggregate sub-phase
  profile. All timings are server+SDK in-process wall time.
- Allocation runs use the counting allocator (separate runs, labeled as
  such; the allocator's atomic adds perturb timings, so allocation numbers
  and timing numbers are never mixed).
- Environment: Intel Core i7-14650HX (24 logical CPUs), 16 GB RAM,
  Windows 11, release, in-process transport.

## 5. What is intentionally NOT measured here

- Real socket networking (in-process transport only) — Phase 23.
- WAL fsync / snapshot / recovery throughput (already measured in
  Phase 15, and the gameplay path runs without persistence in the harness).
- Multi-node / distributed execution — later phases.

## 6. Optimization rule for Phase 21.5

**Optimize nothing.** Fix only measurement bugs. The ranked cost map below
is the input to Phase 22+; any optimization must be justified by these
numbers, re-measured before/after, and validated for determinism and
correctness.
